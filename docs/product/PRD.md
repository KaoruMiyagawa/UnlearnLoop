# UnlearnLoop 产品需求文档

## 1. 文档目的与范围

本文档定义 UnlearnLoop 的产品愿景、第一阶段需求、用户流程和验收标准，服务于后续设计评审、API 设计、数据建模、实现和测试。未进入第一阶段范围的功能不得被表述为已实现。

### 1.1 产品定位

UnlearnLoop 是面向任意知识领域的“错误诊断优先”学习系统。它关注：学习者可能错在哪里？什么新证据最能区分这些可能性？干预后是否能在新情境中独立使用知识？学习流程应由学科无关的引导式工作流承载，Python 只是第一阶段的内容包。

系统输出的是带证据和不确定性的工作判断，不是心理或能力诊断，也不保证仅凭一次作答就能识别真实原因。

### 1.2 目标用户与场景

首要用户是希望学习任意知识领域的自学者，尤其是常在概念边界、执行流程或迁移应用上出错的人。第一阶段用学习 Python 基础和编程思维的用户验证产品流程。次要用户是希望观察学习过程而不替学习者完成作答的教师、导师或研究者。

核心场景：

- 选择变量、条件分支、循环、函数、数据结构等 Python 知识点或短材料。
- 完成文字题或短代码题，系统区分语法错误、概念误解、执行追踪错误、边界条件遗漏、题意理解偏差等候选原因。
- 回答低成本诊断追问后，系统决定解释、继续追问、安排针对性练习或验证另一种假设。
- 完成变式题或新应用场景，更新掌握状态与后续复习建议。

### 1.3 痛点与产品假设

- “答案错了”无法告诉学习者应修正哪种理解。
- 统一讲解可能命中知识点，却没有证据证明学习者已能迁移。
- 学习者和教师难以回看错误如何形成、被何种证据支持或推翻。
- 复习安排通常按时间或章节，而非按未解决的错误模式与遗忘风险。

待验证假设：短而有区分度的追问比立即给出长解释更能提高诊断信息量；迁移验证比重复同型题更能发现“看懂但不会用”。第一阶段通过事件数据和人工抽样评审验证这些假设，不把它们当作既定事实。

## 2. 产品目标与非目标

### 2.1 第一阶段目标

实现一个可追踪、可测试且不绑定学科的引导式学习闭环：选择知识领域和知识点，完成文字或领域适配的作答，生成候选错误假设，回答诊断题，接受一次针对性干预，完成迁移验证，并查看错误历史和复习建议。第一阶段以 Python 内容包作为闭环的具体实现。

### 2.2 非目标

- 不构建通用课程市场、社交系统、教师班级管理或复杂积分体系。
- 不声称模型能准确读取学习者的心理状态、认知风格或长期能力。
- 不支持任意语言的完整代码执行沙箱；短代码先作为文本分析对象，执行能力需单独安全评审。
- 不在视觉评审前实现前端页面。

## 3. 功能清单

### 3.1 第一阶段必须具备

1. 知识点与材料选择：受控知识领域、知识点目录和短材料摘要；第一阶段提供 Python 内容包。
2. 学习会话：生成或选择问题，支持文字答案和代码文本提交。
3. 作答评估：记录答案、题目版本、基础正确性判断、反馈和证据来源。
4. 错误假设：保存候选原因、置信度、支持证据、反证/缺失证据和状态。
5. 诊断追问：选择区分度高、成本合理的问题，并记录选择理由。
6. 干预决策：根据新证据选择继续追问、概念解释、针对性练习或迁移验证。
7. 迁移验证：用不同表面形式但依赖同一知识点的题目验证独立应用。
8. 学习状态：按知识点记录掌握信号、未解决错误模式、最近证据和更新时间。
9. 错误历史与复习：按时间、知识点和错误模式查看记录并生成可解释建议。
10. 可观测性：记录模型提供商、提示版本、耗时、结果状态和可审计决策事件，不记录密钥。

### 3.2 后续扩展

- Ollama 本地模型、多模型比较和模型评估面板。
- 更丰富的代码执行与测试沙箱、项目级练习。
- 教师/导师视图、课程编排、协作复盘。
- 学科插件、知识图谱、用户自定义材料导入。
- 基于历史表现的间隔复习算法与实验对照。

## 4. 关键用户流程

### 4.1 首次学习闭环

选择知识点 → 阅读材料摘要 → 开始学习会话 → 查看问题 → 提交答案 → 获得初步结果和候选错误原因 → 回答诊断追问 → 查看针对性干预 → 完成练习 → 完成迁移验证 → 查看学习状态和复习建议。

每一步显示当前阶段、下一步目的以及“为什么问/为什么推荐”的简短说明；用户可放弃会话，已产生的证据仍保留为未完成记录。

### 4.2 继续诊断

系统发现多个候选原因且信息不足时，状态进入“需要证据”。系统选择预期区分度最高的追问；若成本过高或候选原因已足够集中，则转为解释或练习。回答后，候选原因更新为保留、降低、排除或待验证，并展示变化依据。

### 4.3 复习

打开待复习记录 → 查看上次错误摘要而非完整答案 → 完成变式题 → 更新掌握信号 → 安排下一次复习或标记需要再次诊断。

## 5. 功能验收标准

### 知识点与学习会话

- 可以从至少一组 Python 知识点中选择并开始会话。
- 每个问题拥有稳定 ID、题型、关联知识点、难度/版本信息。
- 提交后可看到处理中、成功和失败状态；重复提交不会产生重复最终事件。

### 错误诊断

- 每个候选错误原因至少包含名称、描述、置信度、支持证据 ID、缺失/反证字段和状态。
- 页面或 API 能回溯某个判断使用的用户输入、模型输出或规则结果。
- 证据不足时允许“信息不足”，不能强制选出单一原因。

### 诊断追问与干预

- 追问包含问题、目标候选原因、预期区分信息和选择原因。
- 新答案会更新候选原因，并产生可重放的决策事件。
- 干预动作来自受控集合，且记录触发条件和下一状态。

### 迁移验证与学习状态

- 迁移题与原题在表面形式或数据上有变化，并关联同一知识点。
- 迁移结果作为新证据参与状态更新，不覆盖历史。
- 状态展示最近证据、变化方向和不确定性，不伪装成精确能力分数。

### 历史与复习

- 可按知识点、状态和时间查看学习事件与错误假设。
- 复习建议说明依据，例如“最近一次迁移验证失败”或“错误模式仍待确认”。
- 无记录时展示可行动空状态；读取失败时保留重试入口且不丢失当前作答。

## 6. 首个版本与成功信号

第一版本只覆盖一个通用的引导式学习流程、内置 Python 内容包、文字/代码文本答案、DeepSeek 单一远程模型、SQLite 单用户本地部署和最小错误历史/复习视图。第一版本不承诺所有学科都有同等深度的题型适配；学科扩展通过内容包和评估器逐步加入。

阶段成功信号不是“模型说得像老师”，而是：流程可端到端运行；每个判断可追溯；决策可用固定输入重放；失败和不确定性可见；至少有人工构造案例验证继续追问、解释、练习和迁移验证四类分支。

## 7. 假设与待确认问题

- 第一阶段是否只支持单用户本地环境，还是需要最小登录/多用户模型？默认按单用户设计。
- 首批 Python 内容包和后续领域内容包由谁维护，是否需要管理界面？默认先使用版本化文件或种子数据。
- DeepSeek 的具体模型、预算、地区可用性和数据保留策略需要确认。
- 是否允许将用户答案发送到远程模型？默认需要明确告知并提供关闭远程调用的错误状态。
- 迁移验证的通过规则由规则、模型还是人工共同决定？默认使用规则约束 + 模型评估 + 可解释记录。
- 复习安排先采用固定、可测试启发式，还是第一阶段就实验间隔算法？默认采用启发式。
